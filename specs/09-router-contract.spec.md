# Spec 09 — Router Contract

> Normative spec for `skills/<name>/` router skills and the intent vocabulary
> (`sheen.vocab.yaml`). Implements root SPEC §4. Establishes the five-step
> disambiguation resolution chain and discriminator field schema.
>
> Status: **Draft v0.1** — tracks ADR-001 and ADR-002.

## 1. Scope

This spec governs:

- The **sheen router skill** (`.github/skills/sheen/`) and any future domain-specific
  router that follows the same pattern.
- The **intent vocabulary file** (`sheen.vocab.yaml`) generated by
  `scripts/build-metadata.ps1`.
- The **five-step disambiguation resolution chain** that all router implementations MUST follow.

It does not govern individual skill or agent files (see Spec 02, Spec 03).

---

## 2. Router Skill Shape

A router skill MUST contain:

```
.github/skills/<router-name>/
├── SKILL.md                       # required — entry point and catalog
├── eval.yaml                      # required — routing evaluation scenarios
└── references/
    ├── authoring.md               # required — discovery + delegation mode docs
    ├── governance.md              # required — keyword routing table, vocabulary registry
    └── factory-patterns.md        # required — multi-agent composition patterns
```

### 2.1 `SKILL.md` requirements

The router `SKILL.md` MUST:

- Declare `category: framework` in frontmatter.
- List all routable agents grouped by domain/pillar in a table.
- Document both **Discovery mode** (catalog browse) and **Delegation mode** (keyword + prompt).
- Include a **Basecoat Integration** section explaining the cross-repo delegate relationship.

### 2.2 `eval.yaml` requirements

Router eval files MUST contain:

- ≥ 5 positive scenarios (`expect_activation: true`) covering discovery and delegation.
- ≥ 3 negative scenarios (`expect_activation: false`) covering cross-domain and off-topic requests.

### 2.3 `references/governance.md` requirements

MUST include:

- A **keyword routing table** with columns: `Keyword(s)`, `Agent`, `Pillar/Category`.
- An **intent vocabulary registry** summary table.
- A **router governance** section with uniqueness and maintenance rules.
- A **cross-repo delegate entry** section documenting the expected entry in the upstream router.

### 2.4 `references/factory-patterns.md` requirements

MUST document ≥ 3 named multi-agent composition patterns. Each pattern MUST include:

1. Name (verb-noun)
2. Trigger conditions (plain language)
3. Composition graph (coordinator → sub-agents, parallel vs. serial)
4. Sub-agent prompt templates for each role
5. Coordinator merge/handoff instructions
6. Exit criteria

## 3. Intent Vocabulary (`sheen.vocab.yaml`)

### 3.1 Generation

`sheen.vocab.yaml` MUST be generated by `scripts/build-metadata.ps1` and MUST NOT be
hand-edited. The intent table is defined in `build-metadata.ps1`; update it there and
re-run the script.

Run `pwsh scripts/build-metadata.ps1 -Check` to validate both `sheen-metadata.json`
and `sheen.vocab.yaml` are current. This check runs in CI as the `catalog-drift` gate.

### 3.2 Schema

```yaml
schema: sheen-vocab/v1
version: "<semver>"           # matches version.json
intents:
  - intent: "<kebab-slug>"    # unique, stable identifier
    keywords: [<str>, …]      # 1–8 trigger words/phrases; lowercase kebab
    skill: "<skill-name>"     # MUST resolve to an entry in skills/ inventory
    agent: "<agent-name>"     # MUST resolve to an entry in agents/ inventory
    discriminator:            # OPTIONAL — required if keyword is cross-domain ambiguous
      artifact_types: [<str>, …]   # nouns that confirm this is the correct intent
      excludes:       [<str>, …]   # nouns that route to a different intent/router
```

### 3.3 Validation rules

| Rule | Severity |
|---|---|
| Every `skill` value MUST resolve to a real skill in the inventory | error |
| Every `agent` value MUST resolve to a real agent in the inventory | error |
| No two intents within `sheen.vocab.yaml` MAY share the same keyword without a `discriminator` | error |
| `discriminator` MUST be present when a keyword also appears in the basecoat governance table | error |
| `sheen.vocab.yaml` MUST be regenerated whenever a skill or agent is added/removed | error (catalog-drift gate) |

## 4. Five-Step Disambiguation Resolution Chain

All router implementations MUST resolve an incoming prompt using the following chain,
in order. The first step that returns exactly one candidate terminates the chain.

```
Step 1 — Exact match
  If the input token exactly matches a single intent's keyword list with no prefix,
  and no other intent shares that keyword: route immediately.
  Tie-breaking rule: longest keyword token wins (ship-it-control-loop > ship-it).

Step 2 — Namespace prefix
  If the input begins with "sheen:" → route within sheen only.
  If the input begins with "basecoat:" → route within basecoat only.
  Ignore all other candidates.

Step 3 — Artifact discriminator
  If the ambiguous intent has a discriminator field:
    - Tokenize the remainder of the user prompt (after the trigger keyword).
    - If any token matches discriminator.artifact_types → score +1 for this intent.
    - If any token matches discriminator.excludes → score -2 for this intent.
    - Select the intent with the highest positive score.
    - If confidence < 0.7 (weak match), proceed to Step 4.

Step 4 — Clarifying question (interactive mode only)
  Present top 2–3 candidates with one-line descriptions.
  Wait for user selection.
  In fleet / autopilot mode: SKIP this step; proceed directly to Step 5.

Step 5 — Fleet / autopilot selection
  Select the highest-confidence candidate.
  Prepend a [ROUTING NOTE] to the output:
    "[ROUTING NOTE] Ambiguous intent '<keyword>' resolved to '<intent>' based on
     context. Override with /sheen:<skill-name> if incorrect."
  Proceed with routing.
```

### 4.1 Canonical cross-domain disambiguation table

| Ambiguous keyword | Nouns → sheen intent | Nouns → basecoat intent | Default |
|---|---|---|---|
| `debate` | component, wireframe, token, brand, flow, pattern, style | pipeline, ci, build | sheen (`design-debate`) |
| `design` | token, theme, brand, layout, component, wireframe | system, architecture, api, service | sheen |
| `ship-it` | *(no suffix → exact match)* | control, loop, gate | `ship-it` skill |
| `rca` | decision, pattern, design-system | incident, outage, alert, failure, build | basecoat (`rca`) |
| `audit` | design, token, brand, a11y, craft, component | security, config, infra, cloud, repo | context → ask |
| `review` | design, component, wireframe, craft, brand | code, pr, pull-request, diff | context → ask |

This table is the authoritative reference. Update it here (and in ADR-002) when new
cross-domain conflicts are discovered.

## 5. Governance

### 5.1 Adding a new router skill

1. Follow the folder shape in §2.
2. Register the new router as a delegate in the upstream router's governance table.
3. Ensure `eval.yaml` meets the minimum scenario counts (§2.2).
4. Add the router's vocabulary file to the `catalog-drift` gate in `checks.json`.

### 5.2 Adding a new intent

1. Add the entry to `$intents` in `scripts/build-metadata.ps1`.
2. If the keyword overlaps with an existing intent or the basecoat keyword table,
   add a `discriminator` block (required per §3.3).
3. Re-run `pwsh scripts/build-metadata.ps1` to regenerate `sheen.vocab.yaml`.
4. Run `pwsh scripts/build-metadata.ps1 -Check` to confirm the check passes.
5. Update `references/governance.md` intent registry summary.

### 5.3 Keyword uniqueness

Within a single router's vocabulary, no two intents MAY share a keyword without a
discriminator. Across routers (sheen + basecoat), shared keywords MUST have a
discriminator in at least one of the two intents.

### 5.4 Stability

Intent slugs are stable once accepted. Rename requires a new intent + deprecation
notice on the old slug for one minor version before removal.
